# Research: TRAI Extension Rebrand

Phase 0 output of `/speckit.plan`. Resolves every technical unknown for the presentation-only rebrand (name "TRAI", tagline "Transcribe with AI", lantern icon) on top of the 001/002/003/004 stack (Chrome MV3 extension + Fastify backend, both esbuild-bundled, vitest-tested). Format per decision: **Decision / Rationale / Alternatives considered**.

## 1. Brand surface inventory: six HTML pages × 3 spots + manifest name — nothing else

- **Decision**: The brand strings live in exactly six HTML files plus `extension/manifest.json`, each in three fixed spots: `<title>` (`Sign in — Video Transcript` / `Transcript — …` / `History — …` / `Notice — …` / `Confirm your email — …` / `Reset password — …`), `<p class="brand-name">Video Transcript</p>`, and `<p class="brand-tagline">language reading room</p>` (identical `<header class="brand">` block from 003 on all six). Grep over `extension/src`, `backend/src`, and `shared` confirms zero references in `.ts` files (no dynamic title or injected brand). The extension's Chrome entry surfaces are the manifest `name` field (management page + toolbar tooltip); `description` ("Transcribe public videos into plain text on demand.") contains no brand string and stays unchanged. `README.md` mentions the old name but is repo-internal developer documentation — out of scope by spec assumption (only `.docs/testcases.md` is a constitution-mandated doc surface).
- **Rationale**: FR-001/FR-002/FR-003/FR-004 require every user-visible surface renamed with zero leftovers. The inventory is exhaustive and small (18 string spots in 7 files), so a scripted or manual replace is verifiable by grep (`0 occurrences of "Video Transcript"` in `extension/src`, `backend/src`, `extension/manifest.json` — spec SC-001/SC-002). No `.ts` logic touches brand text, so the change is purely static HTML + manifest; no page logic, routes, or state change (FR-007).
- **Alternatives considered**: Centralized brand constant injected at build time — rejected (over-build for 18 static strings; would change build.mjs and all six pages for zero behavioral gain; constitution III). Leaving README — accepted per spec assumption (repo-internal docs out of scope, no constitution duty).

## 2. Icon format: Chrome MV3 requires PNG; SVG is the editable source

- **Decision**: Ship a single editable SVG lantern glyph (`extension/src/icons/icon.svg`) and four rasterized PNGs (`icon16.png`, `icon32.png`, `icon48.png`, `icon128.png`) in the same directory. The manifest references only the PNGs: `"icons": { "16": …, "32": …, "48": …, "128": … }` (management page + details view) and `"action": { "default_icon": { "16": …, "32": … } }` (toolbar, incl. 2× DPI which picks the 32 px entry).
- **Rationale**: Chrome's manifest `icons` and `action.default_icon` accept raster formats only — SVG is not supported for extension icons (toolbar and management page render PNG entries). FR-005/FR-006 demand a sharp lantern at 16/32/48/128 px: PNGs at exact sizes render crisply at 1× and 2× without browser downscaling artifacts. The SVG stays as the single design source of truth so future tweaks re-rasterize from one file (spec assumption: "the mark's design is the source of truth").
- **Alternatives considered**: SVG referenced directly in `icons` — rejected (unsupported by Chrome; would silently fall back to the generic placeholder, violating FR-005). Single 128 px PNG scaled down — rejected (downscaling softens the 16 px toolbar glyph; spec demands sharp at every displayed size, SC-003). CSS-only lantern as icon — impossible (toolbar icons are image files, not CSS).

## 3. Icon generation: one-time rasterize on macOS, commit PNGs, build only copies

- **Decision**: The four PNGs are generated once from `icon.svg` with the macOS built-in QuickLook renderer and committed (`qlmanage -t -s <size> -o <dir> icon.svg` → rename to `icon<size>.png`; `sips` cannot rasterize SVG, `rsvg-convert`/`inkscape`/`imagemagick` are not installed on this machine). `extension/build.mjs` `copyStatic()` gains an icons copy step (`src/icons/*.png` → `dist/icons/`); the build never rasterizes — dist is wiped and regenerated from committed sources on every build (existing pattern: manifest, pages, theme.css are copied; build outputs are gitignored).
- **Rationale**: FR-006/FR-009 require the regenerated build output to contain the four sizes, and every build must regenerate dist — copying committed PNGs satisfies both with zero new dependencies (no `sharp`, no canvas, no binary tool in the build path; constitution III). One-time generation is a documented dev action, not part of `npm run build`, so builds stay deterministic on any machine. `qlmanage` renders SVG with a transparent background, matching the paper-palette icon design.
- **Alternatives considered**: `sharp` devDependency — rejected (adds native dep for a four-file one-time rasterization; constitution III minimal scope). `sips` — rejected (does not read SVG). Commit the SVG only and rasterize in-build — rejected (no installed rasterizer; would add a dependency or platform-specific tool to the build). Hand-drawn PNGs without SVG — rejected (loses the editable source of truth).

## 4. Lantern glyph design: derive from 003's CSS lantern mark and palette

- **Decision**: The icon is a lantern-only glyph (no text, no wordmark) reproducing 003's CSS lantern (`shared/theme.css` `.lantern`): warm-gold rounded body (`--gold #E8A33D` with `--gold-deep #B7791F` vertical edge stripes), paper-colored window slats (`--paper-card #FFFDF8` repeating vertical bars), gold-deep cap and tassel, optional soft indigo (`--indigo #403B8C`) accent line — all within 003's exact token palette. Design scales the mark into a full-bleed square canvas (transparent background) with the glyph occupying ~85% of the viewBox so it reads at 16 px.
- **Rationale**: FR-005 demands "derived from the Paper Lantern theme's lantern mark … consistent with its palette". Drawing the glyph from the same tokens and silhouette keeps the toolbar icon visually identical in character to the in-page lantern (spec SC-007: instant recognition), while 003's `text-transform`/size rules do not apply to raster assets. `aria-hidden`-style concerns don't apply (toolbar icons are not in the page a11y tree).
- **Alternatives considered**: Reuse the CSS `.lantern` via a screenshot — rejected (CSS box-shadow/gradient rendering is page-context dependent; a static SVG is the durable source). New logo design — rejected (spec assumption: the mark's design is the source of truth; no new logo or wordmark).

## 5. Tagline case: `.brand-tagline` `text-transform: lowercase` would render "transcribe with ai" — must be disabled

- **Decision**: `shared/theme.css` `.brand-tagline` drops `text-transform: lowercase` (one property removed; the rule keeps its `--ink-soft` color, 0.72rem size, and letter-spacing). The tagline markup becomes exactly `Transcribe with AI` on all six pages.
- **Rationale**: 003 styled the old tagline with `text-transform: lowercase` (cosmetic — "language reading room" was already lowercase). Applied to "Transcribe with AI" it would render "transcribe with ai", violating the spec's exact wording (FR-003/FR-004; spec Assumptions: "exactly 'Transcribe with AI'"). Removing the transform makes the authored text the rendered text; "AI" stays uppercase. Both build outputs copy `shared/theme.css`, so one edit covers all six pages (extension dist + backend dist/auth/pages). This is the only theme.css change and it is tagline-presentation only (FR-011).
- **Alternatives considered**: Author the tagline as "Transcribe with ai" — rejected (exact wording demands "AI"). `text-transform: capitalize` — rejected (would also capitalize the "w" mid-phrase incorrectly and still lowercase "AI"). Per-page inline style overrides — rejected (six overrides vs one shared rule; `[hidden]`/theme integration rule from 003 contracts keeps styling in the shared sheet).

## 6. Tagline fits: "Transcribe with AI" is shorter than the old tagline — no layout work

- **Decision**: No layout changes. "Transcribe with AI" (16 chars incl. spaces) is shorter than "language reading room" (21 chars), same single-line position under the brand name in the 003 header; the 44rem body max-width and header flex layout already accommodate it at desktop and narrow widths (spec edge case).
- **Rationale**: The spec edge case asks only that the longer tagline not wrap awkwardly or scroll horizontally; the new tagline is 5 chars shorter, so the concern is moot by construction. 003's responsive work (viewport meta, reflow) is unchanged.
- **Alternatives considered**: Responsive font-size rules — rejected (nothing to fix; no measurable need).

## 7. `.docs/testcases.md` staleness: two rows stale, two edits required

- **Decision**: Per constitution "Regression checklist currency", the plan evaluates the canonical checklist and records required edits (applied in the implementation change, FR-009): (a) `extension` row pass criterion "chrome://extensions shows Video Transcript" → "shows TRAI", plus new icon checks — `dist/icons/icon{16,32,48,128}.png` present and the lantern icon renders in toolbar + management page; (b) `build` row gains a criterion that the rebuilt dist contains the new name (manifest) and the four icon files. Rows `backend`, `signin`, `transcribe`, `transcript-actions` are untouched (FR-007 — behavior unchanged; their pass criteria stay valid).
- **Rationale**: The `extension` row's pass criterion names the old brand, so it is stale the moment the manifest name changes (a stale checklist silently drops the brand check on the next suite run — the exact failure mode the constitution clause exists to prevent). The `build` row is the canonical place for the regenerated-assets check (FR-009c). No other row references brand text or icons.
- **Alternatives considered**: Leave testcases.md untouched — rejected (constitution MUST; spec FR-009). Add a new dedicated row instead of editing `extension` — rejected (the stale criterion would still sit in the `extension` row; edit-in-place keeps one row per surface).

## 8. Test strategy: asset-only exception — no new behavioral tests, suites prove zero drift

- **Decision**: No new automated behavioral tests. The rebrand is presentation/asset-only (no behavior change), so constitution I's "asset-only changes MAY skip behavioral tests with an explicit exception noted in the task" applies — the exception is recorded in plan.md and carried into tasks.md. Verification = existing suites stay green (`extension/tests`: 8 suites incl. `toolbar.test.ts` — which tests click-behavior, not manifest name/icons, so it is unaffected; `backend/tests`: 5 suites), plus `npm run build` in both projects (regenerates dist with new assets), plus quickstart manual scenarios B1–B8, plus the `.docs/testcases.md` rows updated in §7.
- **Rationale**: FR-007/FR-011 guarantee zero behavior change; a behavioral test would test nothing (there is no new logic to fail). The existing 13 suites are the regression net that proves the rebrand moved nothing (SC-004); the manual scenarios are the visible-surface proof (SC-001/002/003/007). This mirrors 003's asset/CSS precedent (visual checks via quickstart, logic suites untouched).
- **Alternatives considered**: Unit test asserting manifest JSON content — rejected (asserts static data, not behavior; adds a test file that must churn on every rebrand; constitution I's exception exists exactly for this case). Snapshot test of the six HTML files — rejected (brittle, no behavioral signal).

## Manual configuration required (not code)

- **Icon rasterization**: one-time, documented dev step (macOS): `qlmanage -t -s 16|32|48|128 -o /tmp/icons extension/src/icons/icon.svg` → rename outputs to `icon{size}.png`, verify transparency + legibility at 16 px, commit. Not part of the build (research #3).
- **Branch**: create `005-trai-extension-rebrand` from current work (`004-transcript-copy-actions`, implemented) before implementation — no code changes land on the 004 branch (002/003/004 precedent).
- **Backend**: no source logic change, but the two auth HTML pages change → backend must be rebuilt/redeployed (its `build-auth.mjs` copies the HTML into `dist/auth/pages`); no env, migration, or dashboard change.
- **Regression impact**: `.docs/testcases.md` `extension` + `build` rows updated in the same change (§7); `quickstart.md` created (this feature); 001–004 quickstart scenarios remain the regression gate and stay valid.
